vdi-tool does not invent its own measuring instruments. It uses established tools for the measuring and adds the parts around them: deploying the desktops, starting every desktop at the same moment, checking the result against a second source, and reporting.

A2. How the pieces talk to each other

Two things in this picture matter for trust in the numbers:

  • The load is real. Every byte goes from a real virtual machine through the virtual disk, QEMU and the Proxmox storage layer to the storage. Nothing is simulated on the host.
  • There are two independent measurements. The desktop says what it did (fio or DiskSpd). Proxmox says what it saw on that desktop's disk. The tool compares them (section A7).

A3. fio: disk workloads on Linux desktops

fio (flexible I/O tester) is the standard open tool for storage benchmarking. It issues reads and writes in a pattern you describe and times every single one.

How fio works

You tell fio four things: what kind of I/O (random or sequential, read or write or a mix), how big each request is (block size), how many requests to keep in flight at once (queue depth), and how many parallel workers to run (jobs). fio then keeps that many requests outstanding against a test file for a set time and records how long each one took.

SettingMeaningEffect
rwrandread, randwrite, randrw (random), read, write, rw (sequential)Random stresses IOPS and latency; sequential stresses throughput.
rwmixreadShare of reads in a mix, in percent70 means 70% reads, 30% writes.
bs or bssplitRequest size, or a weighted mix of sizes4k for small-block work, 1M for throughput. 4k/60:8k/20:16k/10:64k/10 is a realistic desktop mix.
iodepthRequests in flight per jobHigher depth means more pressure and higher latency.
numjobsParallel workersMultiplies the pressure; total in flight is jobs times depth.
rate_iopsA cap on IOPSTurns a stress test into a steady, user-like load.

How vdi-tool runs it

  1. Clean up. Any fio or agent left from an earlier run is stopped.
  2. Prepare the test file with real data. The file (1 GB by default, settable per run) is written once with random data that cannot be compressed or deduplicated, straight to disk, and flushed. A marker file lets later runs reuse it.
  3. Report ready and wait. The desktop tells the tool it is prepared and then asks every 2 seconds whether to go.
  4. Go together. When all desktops are ready (or 90% are ready and nothing has changed for 2 minutes), the tool says go and every desktop starts the timed run at the same moment.
  5. Timed run. fio runs for exactly the chosen duration and prints its result as JSON.
  6. Report. The agent posts IOPS, MB/s and latency (average, p50, p95, p99, maximum) for reads and for writes.

The preparation command:

fio --name=prep --filename=test.dat --size=4G --rw=write --bs=1M --ioengine=libaio --iodepth=8
    --direct=1 --refill_buffers=1 --fallocate=none --end_fsync=1

The timed command for the disk stress workload:

fio --name=vdi --filename=test.dat --size=4G --rw=randrw --rwmixread=70 --bs=4k --iodepth=16 --numjobs=1
    --group_reporting --ioengine=libaio --direct=1 --fallocate=none --time_based --runtime=120 --output-format=json
OptionWhy it is there
--direct=1Bypasses the desktop's own memory cache, so every request really reaches the virtual disk.
--ioengine=libaioLinux asynchronous I/O, which is what makes a queue depth above 1 real.
--refill_buffers=1Fresh random data for every block, so an array cannot shrink it with compression or deduplication.
--fallocate=noneStops fio from only reserving the file. A reserved but unwritten file reads back as zeros without touching the storage.
--end_fsync=1Makes sure the prepared data is on the storage before the timed run begins.
--time_based --runtimeRuns for a fixed time, looping over the file if needed, so all desktops load the storage for the same window.
--group_reportingOne combined result for all jobs in the desktop.
Why the preparation step exists. In early testing the file was only reserved, never written. Reads came back as zeros from the thin pool without any real I/O, and the tool reported 175 Gbit/s from a single drive. Writing real data first, and cross-checking with Proxmox, is what makes the current numbers trustworthy.

The disk workloads in the library

A detail about rate caps. When a mix of block sizes is used, fio counts a rate cap in units of the smallest block. The tool scales the cap by the average block size so that "25 IOPS" really means 25 operations per second. Measured: exactly 25 per desktop.

A4. DiskSpd: disk workloads on Windows desktops

DiskSpd is Microsoft's storage load tool, the Windows counterpart of fio. The same workload definitions are translated to DiskSpd switches, so a Linux and a Windows batch can be compared.

The tool keeps one copy of diskspd.exe (downloaded from Microsoft's GitHub releases at install time) and each Windows desktop fetches it on first use. The agent is a PowerShell script that follows the same steps as on Linux: write the test file with random data using write-through, report ready, wait for go, run, parse DiskSpd's XML result and report.

Latency-L -RxmlRecords per-request latency and prints percentiles as XML.
Rate cap-g25iIOPS limit per thread.

Windows clones are started through the guest agent in the same way as Linux ones. Because the guest agent has no desktop session, the PowerShell agent is launched as a detached process and reports over HTTP. The office, CPU and fill workloads are Linux only for now.

A5. The built-in workloads: office, CPU, fill and boot storm

Office worker (synthetic)

A loop of five actions with a random pause of 0.5 to 2 seconds between them, like a person working. Each action is timed, so the result is a response time, not a throughput.

ActionWhat it doesWhat it loads
SaveWrites a 2 to 8 MB document and forces it to disk.Storage writes
OpenReads the document back from disk, not from memory.Storage reads
CompressCompresses 4 MB.CPU
ComputeHashes 48 MB.CPU
DownloadFetches a file from the tool over the network.Network

The report shows the average and p95 time per action. When the host or storage is overloaded, those times rise. This workload uses no real office applications; EUC Score (section A10) is the tool for that.

CPU stress

One worker per virtual core, each hashing data in a tight loop for the whole run. The result is the total work done per second. It shows how far the host's CPUs can be oversubscribed before every desktop slows down.

Fill disk

Writes fresh random data into the desktop and leaves it there. It is for capacity tests: how full can the pool or array get, how does performance change as it fills, and how much does thin provisioning really save. The data is random on purpose so that compression and deduplication cannot hide it. It stops at the size you ask for, when the time limit is reached, or when the desktop has 2 GB left.

Boot storm

The classic VDI morning. The tool stops every desktop in the batch, then starts them all at once through Proxmox and times each one until its guest agent answers. No software runs inside the desktop for this; the measurement is taken from outside. The result is the time until each desktop is usable, with the mean and the slowest. It works for Linux and Windows.

A6. QEMU guest agent and cloud-init: how work gets into a desktop

QEMU guest agent

The guest agent is a small service inside each desktop that listens on a private channel to the hypervisor. Through the Proxmox API the tool can ask it to run a command, without a network login, SSH key or password. That is how a run starts on hundreds of desktops in a few seconds, and it works the same on Linux and Windows.

The command the tool sends is short: download the workload agent from the tool and start it in the background with the workload description, the duration and the address to report to. From then on the desktop talks to the tool over plain HTTP. The guest agent is also how the tool renames Windows clones and asks a desktop what went wrong when it fails to report.

cloud-init

cloud-init is the standard first-boot configurator for Linux images. vdi-tool acts as its own configuration server: every clone gets a small identifier in its virtual hardware (the SMBIOS serial number) that points cloud-init at the tool, which answers with that desktop's name, user and setup script. No configuration drive has to be built per clone, which is one reason 100 linked clones deploy in about a minute.

Windows unattended setup

For Windows the template is built from the Microsoft ISO with an answer file the tool generates. Setup runs without any clicks, installs the VirtIO drivers and the guest agent, turns on Remote Desktop and shuts down so the machine can become a template.

A7. Proxmox counters and the validity check

A benchmark that only trusts its own load generator can be fooled. vdi-tool checks every disk run against a second, independent source.

During a run the tool reads Proxmox's own counters every 10 seconds: host CPU and memory, and for the desktops in the run their disk bytes read and written and network bytes in and out. These come from the hypervisor, not from inside the desktops.

CheckRuleResult
Desktops that failedMore than 10% of the batch failed or did not reportNot valid: totals understate the batch.
Some failed, 10% or fewerValid with a note.
Real dataThe run predates the real-data preparationNot valid.
Cross-checkDesktops claim more than 1.5 times the throughput Proxmox saw on their disksNot valid: part of the I/O never reached the storage.

Only samples from the timed window count, so preparation does not blur the result. The same samples give the report its "what limited this run" sentence: for example, host CPU at 88% during a 4k random run points at the host, not the drive.

A8. Prometheus, the exporters and Grafana

These three are the standard open monitoring stack. vdi-tool installs and configures them in its container.

PieceHow it works
Proxmox exporterAsks the Proxmox API for the state of every VM, node and storage and publishes it as metrics: CPU, memory, disk and network counters, storage usage.
vdi-tool /metricsThe tool publishes its own run results: whether a run is in progress, desktops by state, and for each finished run its IOPS, throughput, latency, host CPU and validity, labelled by workload, storage and clone type.
Node exporterReads the host kernel's counters: bytes, errors and drops per network port, IOPS and latency per disk, CPU by kind of work, memory, pressure. Needed for the per-link view of the 100 Gb ports.
PrometheusCollects ("scrapes") all of the above every 15 seconds and keeps the history, so any past run can be looked at again.
GrafanaDraws dashboards from Prometheus. Counters are turned into rates, for example bytes per second averaged over one minute.

The dashboards

DashboardQuestion it answers
VDI overviewWhat is the host doing right now? Desktops running, host CPU and memory, total desktop disk and network, the ten busiest desktops, storage used, the run in progress.
VDI benchmark runsHow do the runs compare? IOPS, throughput, p95 latency, peak host CPU and validity per run, filtered by workload, storage and clone type.
VDI desktop drilldownWhich desktop is the odd one out? CPU, memory, disk and network for one desktop or any group, and the spread from slowest to fastest.
VDI storage and network linksWhere is the bottleneck: network, storage or host? Per port throughput against the 400 Gb/s ceiling, errors and drops, per disk IOPS and latency. Needs the node exporter.

A9. Density tests: finding how many desktops fit

A single run answers "how fast". A density test answers the sizing question: "how many desktops before users notice".

The tool runs the same workload several times on a growing part of the batch, for example 25, 50, 75 and 100 desktops, and plots latency and per-desktop performance against the number of desktops. You give a target, such as p95 latency under 5 ms, and the report states the largest step that met it.

Uncapped stress finds the ceiling: total IOPS levels off after about 25 desktops and latency climbs from there. A capped, user-like load barely registers: latency is flat to 100 desktops, so this drive's limit for office users is far beyond 100.

A10. EUC Score: measuring what the user feels

Everything above measures the infrastructure. EUC Score measures the experience: how quickly applications respond and how smooth the screen is inside a real desktop session.

How EUC Score works

  • Simloads are scripted workloads that drive real applications on screen: single applications (type 1), blended personas such as a knowledge worker (type 2), and score tests (type 3).
  • Each Simload is a program with a simple command line, for example SL1-NotepadEdit.exe run 120 to run for 120 seconds. Installed Simloads are listed in the Windows registry under HKLM\Software\EUCScore\Simloads.
  • Telemetry is collected once per second into a CSV file, and each Simload writes a log, both in C:\EUCScore\Results.
  • For the full visual score, a physical endpoint device connects to the desktop over the remote display protocol and a capture device records the screen. That part is outside vdi-tool.

How it fits with vdi-tool

vdi-tool deploys the desktops and puts background load on most of them. EUC Score runs on a few "probe" Windows desktops at the same time. The combined answer is the one a sizing decision needs: at N desktops on this storage, this is what a user experiences.

StepState
Upload the EUC Score base package to the tool (Templates page)Available

Licence. EUC Score is not part of vdi-tool and the tool never downloads it. You download it from eucscore.com and accept its agreement. The base package is freeware, but organizations with more than 50 users or over US$1M revenue need a paid subscription, and the Enterprise Simloads need a licence file. Simloads need a logged-on Windows session, which is why the template option keeps the user logged on; that stores the password in the Windows registry, so use it for test desktops only.

A11. Reading the numbers

TermMeaningGood to know
IOPSRead and write operations completed per second.Only comparable at the same block size.
Throughput (MB/s, GB/s)Data moved per second. IOPS times block size.1 GB/s is 8 Gbit/s on the wire.
LatencyTime from sending one request to getting its answer.This is what a user feels as "slow".
p50, p95, p9950%, 95% or 99% of requests were at least this fast.p95 and p99 show the bad moments an average hides. Size on p95, not on the average.
Queue depthRequests in flight at once.More depth raises IOPS until the device is saturated, then only latency rises.
Block sizeSize of each request.Small blocks test IOPS and CPU cost per request; large blocks test bandwidth.
Peak host CPUHighest host CPU use during the timed window.Above about 85% the host, not the storage, is likely the limit.
Valid, warning, not validThe tool's own judgement of the run (section A7).Never quote a run marked not valid.

Three habits that keep results honest

  1. Compare like with like. Same workload, same duration, same number of desktops, same clone type. Change one thing at a time.
  2. Look at latency next to throughput. A higher number with ten times the latency is not a better result for users.
  3. Check what limited the run. If the host CPU was the limit, a faster array will not change the number.
